 # 🧠 1. First understand what Git actually does

 Think of your project as having **4 places**:

```
Your files
   ↓
Working Directory
   ↓ git add
Staging Area
   ↓ git commit
Local Repository
   ↓ git push
GitHub Repository
```

 And going the other way:

```
GitHub
   ↓ git pull
Local Repository / Working Directory
```

 The most important distinction:

 ### `git add`

 Means:

 > "I want this change to be included in my next commit."

 ### `git commit`

 Means:

 > "Save this group of changes as a version in my local Git history."

 ### `git push`

 Means:

 > "Send my local commits to GitHub."

 ### `git pull`

 Means:

 > "Get changes from GitHub and integrate them into my local project."

---

 # 2\. `git status` — your best friend ⭐

 Run this constantly:

```
git status
```

 It tells you:

 - which files are modified
- which files are new
- which files are staged
- which branch you're on
- whether your local branch is ahead/behind GitHub

 Example:

```
modified: BST.py
new file: Graph.py
```

 Then:

```
git add .
```

 and:

```
git status
```

 Now Git might say:

```
Changes to be committed:
    modified: BST.py
    new file: Graph.py
```

 This is one of the most useful commands to learn.

---

 # 3\. `git diff` — see exactly what changed

 Suppose you modified `BST.py`.

 Before committing:

```
git diff
```

 This shows the actual changes you made.

 For example:

```
- print("Binary Tree")
+ print("Binary Search Tree")
```

 This is extremely useful because you can inspect your work **before committing**.

---

 # 4\. Staging is actually important

 Suppose you have:

```
BST.py       modified
DFS.py       modified
README.md    modified
```

 You only want to commit the Python files.

 Do:

```
git add BST.py DFS.py
```

 Then:

```
git commit -m "Update tree and graph algorithms"
```

 `README.md` remains uncommitted.

 This is why the staging area exists.

 # 5\. `git log` — see your history

 Run:

```
git log
```

 You'll see previous commits.

 A more readable version:

```
git log --oneline
```

 Example:

```

9a23bc1 Initial commit
```

 This is basically the history of your project.

 # 6\. `git show` — inspect a particular commit

 Suppose:

 gives:

```

 You can inspect the first commit:

```
git show a81f32d
```

 It shows what changed in that commit.

 # 7\. `.gitignore` — VERY important

 You don't want every file on your computer going to GitHub.

 For Python projects, you might have:

```
__pycache__/
*.pyc
.env
venv/
.venv/
```

 Create:

```
.gitignore
```

 Example:

```
__pycache__/
*.pyc
.venv/
venv/
.env
```

 Then:

```
git add .
git commit -m "Add gitignore"
git push
```

 ### Why?

 You don't want things like:

```
passwords
API keys
virtual environments
Python cache files
IDE settings
```

 uploaded to GitHub.

 **Never commit passwords, API keys, tokens, or other secrets.**

 # 8\. `git clone` vs `git init`

 This confuses almost everyone initially.

 ### `git clone`

 Use when a repository **already exists on GitHub**.

```
git clone https://github.com/username/project.git
```

 It downloads the repository and connects it to GitHub.

---

 ### `git init`

 Use when you have a **brand-new local project** and want to turn it into a Git repository.

 For example:

```
mkdir my-project
cd my-project

git init
```

 Then:

```
git add .
git commit -m "Initial commit"
```

 Eventually you can connect it to GitHub with a remote.

 # 9\. Remote — understand this concept

 Your local Git repository needs to know where GitHub is.

 Check:

```
git remote -v
```

 You might see:

```
origin  https://github.com/573-pankaj/DSA-WITH-PYTHON.git
```

 `origin` is simply the conventional name given to your GitHub repository.

 So:

```
git push origin main
```

 basically means:

 > Push my `main` branch to the remote repository called `origin`.

 You can also usually just do:

```
git push
```

 once the upstream relationship is configured.

 # 10\. `git pull` — VERY important

 Imagine:

```
GitHub
   ↑
someone changed something
```

 Your local copy doesn't have that change.

 Run:

```
git pull
```

 Git downloads the changes and integrates them into your current branch.

 A very common workflow is:

```
git pull
# make changes
git add .
git commit -m "My changes"
git push
```

 This becomes especially important when working with other people.

 # 11\. Branches 🌿 — one of Git's most important concepts

 Imagine your `main` branch:

```
A --- B --- C
```

 You want to experiment with a new feature.

 Create a branch:

```
git branch feature
```

 Switch to it:

```
git switch feature
```

 Or do both at once:

```
git switch -c feature
```

 Now:

```
             D --- E
            /
A --- B --- C
            main
```

 Your experimental work is separated from `main`.

---

 # 12\. See your branches

```
git branch
```

 Example:

```
* feature
  main
```

 The `*` means you're currently on `feature`.

 Switch back:

```
git switch main
```

 # 13\. Merge a branch

 Suppose you've finished your feature:

```
git switch main
```

 Then:

```
git merge feature
```

 Now the changes from `feature` are brought into `main`.

 Then:

```
git push
```

 # 14\. The concept of a Merge Conflict ⚠️

 This is something you'll eventually encounter.

 Imagine you and another person both modify:

```
BST.py
```

 in different ways.

 Git may say:

```
CONFLICT (content): Merge conflict in BST.py
```

 You'll see something like:

```
<<<<<<< HEAD
print("My version")
=======
print("Other version")
>>>>>>> feature
```

 You manually decide which code should remain.

 Then:

```
git add BST.py
git commit -m "Resolve merge conflict"
```

 Don't panic when you see a conflict. It's Git asking:

 > "Which version do you actually want?"

---

 # 15\. Undoing changes — VERY useful

 There are different kinds of "undo."

 ### You modified a file but haven't staged it

```
git restore BST.py
```

 This discards your local modification.

 ⚠️ Be careful: your changes are lost.

---

 ### You staged a file but don't want to commit it

```
git restore --staged BST.py
```

 This removes it from staging but keeps your modifications.

---

 # 16\. Undo your last commit

 If you committed something locally by mistake:

```
git reset --soft HEAD~1
```

 This removes the commit but keeps your changes staged.

 There's also:

```
git reset --mixed HEAD~1
```

 which removes the commit and unstages the changes.

 ### Be careful with:

```
git reset --hard
```

 It can permanently discard changes.

 Don't use `--hard` casually.

---

 # 17\. `git stash` — your temporary drawer 🗄️

 Imagine you're working on:

```
BST.py
```

 You've made changes, but suddenly you need to switch branches.

 You aren't ready to commit yet.

 Use:

```
git stash
```

 Git temporarily puts your modifications aside.

 Now you can switch branches:

```
git switch main
```

 Later:

```
git stash pop
```

 Your changes come back.

 Very useful.

 Then:

 Tags are useful for marking releases:

```
